# Зафиксированные требования пользователя к Hori

Это короткая фиксация конкретных требований, а не общее описание характера бота.

## 1. Базовая цель

- Hori должна ощущаться как один цельный персонаж, а не как ассистент или набор режимов.
- У персонажа должны быть заметные «нотки шизы», злоба, социальная цепкость и чувство сцены.
- Система должна оставаться дешёвой, cache-friendly и без тяжёлого hot path.

## 2. Core prompt

- Core prompt у всех один.
- Нельзя делать отдельный core под каждого пользователя.
- Отношения с человеком не должны менять сам core.
- Core должен меняться эпохами раз в несколько часов.
- Смена эпохи должна быть заметной, а не декоративной.
- При этом это всё ещё одна и та же Hori, а не набор разных ботов.

## 3. Что должно быть отдельно от core

- Relationship Overlay должен быть отдельным блоком.
- Persistent hooks должны быть отдельным блоком.
- Сжатая история текущей сессии должна быть отдельным блоком.
- Живое окно сообщений должно быть отдельным блоком.

## 4. Итоговый порядок prompt-блоков

1. Один общий epoch core.
2. Блок hooks.
3. Сжатый контекст текущей сессии.
4. Живое окно сообщений.
5. Короткий relationship tail для текущего target user.

Смысл схемы: общий характер Hori не смешивается с персональными рычагами, а live chat не тонет в старой истории.

## 5. Требования к relationship

- Relationship относится только к текущему адресату ответа.
- Это должен быть короткий блок, а не длинная психологическая простыня.
- Блок задаёт дистанцию, жёсткость, допустимость поддёва и тон ответа.

## 6. Требования к hooks

- Hooks нужны не как «факты о человеке», а как social callbacks.
- Бот должен искать, на что человека можно обидеть, затроллить или пристыдить.
- У hook должно быть направление применения: когда он уместен, а когда нет.
- Максимум 5 hooks на человека.
- Hooks должны быть persistent, а не одноразовым мусором.
- Нельзя тащить в hooks мелочи, которые не переживают время.
- Нельзя вспоминать hooks не к месту.

## 7. Как анализировать участников

- После сессии бот берёт общий диалог и анализирует участников по очереди.
- Нельзя делать один жирный социальный анализ на всех сразу.
- Для каждого участника должен быть отдельный прогон по тому же общему диалогу.
- В один такой анализ нельзя пихать больше 100 сообщений.

## 8. Требования к окну сообщений

- В live window должны попадать только пользовательские сообщения.
- Из сообщений Hori туда должны попадать только реально отправленные ответы.
- Нельзя включать queued, unsent, draft или предполагаемые бот-реплики.
- Порядок сообщений должен оставаться реальным.

## 9. Мультиюзерный чат

- Hori должна жить в общем чате, а не только в диалоге один на один.
- Система не должна терять target user текущего ответа.
- Система не должна терять последнего говорящего.
- Бот может отвечать одним полотном сразу в общую сцену, но адресат всё равно должен быть ясен.
- Для bot turns нужен target metadata слой.

## 10. Компрессия истории

- Когда в сессии набирается 54 сообщения, первые 46 уходят на компрессию.
- Последние 8 остаются живыми.
- Компрессию должна делать дешёвая модель.
- Выход компрессии должен быть коротким и жёстким, а не литературным summary.
- Получившаяся сводка вставляется перед live window.

## 11. Session lifecycle

- Сессия закрывается после 10 минут тишины.
- Если в сессии был хотя бы один compaction, после закрытия начинается 20-минутный sleep.
- Во время sleep Hori не отвечает.
- Во время sleep должны идти offline relationship evaluation и hook evaluation.

## 12. Чего пользователь не хочет

- Per-user core.
- Relationship, который определяет всю личность Hori.
- Раздутый prompt с множеством тяжёлых блоков.
- Hooks из случайной ерунды.
- Social callbacks не к месту.
- Неотправленные бот-реплики в prompt.
- Архитектуру, которая ломает cache и делает систему дорогой.
- Бесконечный брейншторм вместо реализации.

## 13. Сжатая формула

Пользователь требует Hori с одним общим epoch core, отдельным relationship, отдельными persistent hooks, дешёвой компрессией старой части сессии, sent-only live window, мультиюзерной continuity без потери target user и post-session анализом участников по очереди. Всё это должно давать не «умного ассистента», а цельного, злого и странного персонажа без раздувания стоимости и hot path.
