# Hori — Detailed Plan: Epoch Core + Ladder Chat Memory

> Статус: draft source of truth.
> Это подробный план целевой системы, которую пользователь описал в чате.
> Если будущие решения противоречат этому файлу, приоритет у этого файла и у прямых уточнений пользователя.

## 0. Суть системы в одном абзаце

Хори работает вокруг одного общего CorePrompt, который одинаков для всех пользователей и меняется не по каждому сообщению и не по отношениям, а глобальными эпохами раз в несколько часов. В горячем пути prompt должен быть максимально стабильным ради cache hit: один общий core, короткий блок persistent hooks для текущего target-пользователя, блок сжатого контекста старых сегментов текущей сессии, затем живое окно чата в виде аккуратной лесенки из пользовательских сообщений и реально отправленных ответов Хори, и только в самом конце маленький relationship block по тому человеку, которому Хори отвечает сейчас. Когда история разрастается, при накоплении 54 элементов живой лестницы первые 46 уходят в async compaction дешёвой моделью, а в live window остаётся свежий хвост. После 10 минут тишины сессия закрывается; если в ней был хотя бы один compaction, Хори на 20 минут уходит в sleep, ник меняется на «спит» по возможности, новых ответов нет, а в фоне по каждому участнику обновляются relationship и hooks.

## 1. Что именно считается целевой архитектурой

### 1.1. Неподвижные правила

1. CorePrompt один на всех.
2. CorePrompt не зависит от конкретного пользователя.
3. CorePrompt не переключается на каждый message.
4. CorePrompt резко меняется только эпохами, примерно каждые 2-4 часа.
5. Relationship не встроен в core и живёт отдельно.
6. Hooks не встроены в core и живут отдельно.
7. История в prompt должна быть подана не сырой общей лентой, а лесенкой user -> Hori -> user -> Hori в фактическом порядке ответов.
8. Если бот ещё не ответил и сообщение стоит в queue, такой bot turn в prompt не попадает.
9. Если текущее входящее сообщение прямо сейчас обрабатывается, оно временно добавляется в самый конец live window как последний незавершённый ход.
10. Старая часть сессии не держится сырым текстом бесконечно: она сжимается сегментами.
11. Compaction не запускается после 46 сообщений. Правильное правило: при 54 сообщениях первые 46 уходят на обработку, хвост остаётся живым.
12. После завершения сессии анализ отношений и hooks идёт асинхронно, не в hot path.

### 1.2. Главная цель

Сделать систему одновременно:

- шизовой и живой по характеру;
- дешёвой по prompt cache;
- устойчивой в мультиюзерном чате;
- не раздутой десятком больших prompt-блоков;
- пригодной для долгого диалога без потери continuity.

## 2. Почему выбран именно этот дизайн

Проблема в том, что дешёвая модель начинает плавать, если ей каждый раз менять большой system prompt, подмешивать длинные relationship-инструкции по разным людям и кидать общую кашу из группового чата без адресации. Поэтому финальный дизайн держится на трёх принципах.

### 2.1. Максимально стабильный hot path

Почти весь prompt должен меняться медленно или монотонно.

- Core epoch меняется редко.
- Compacted context меняется кусками, не на каждом ходе.
- Hooks обновляются только после сессии.
- Relationship tail короткий.
- Live ladder chat растёт предсказуемо и потом сегментно схлопывается.

Это даёт хороший cache reuse, потому что 99% prompt-пакета остаётся тем же самым, а меняется в основном нижний хвост и текущее сообщение.

### 2.2. Один активный target user на один ответ

Даже в групповом чате Хори в рамках одного конкретного ответа должна понимать, кому она отвечает сейчас. Иначе relationship block, hooks и continuity начнут смешиваться между людьми.

### 2.3. Offline social analysis вместо постоянного самоанализа

Hooks и relationship нельзя дёшево и стабильно пересчитывать на каждом ходе. Значит, они обновляются пакетно после закрытия сессии, когда уже есть весь compacted context и хвост живой сцены.

## 3. Финальный prompt contract

Итоговая форма prompt должна быть короткой, жёсткой и стабильной. Не возвращать старый тяжёлый composer из множества динамических подсистем.

Физический порядок блоков должен быть таким.

### Block 1. Core Epoch

Это единственный system-level характер Хори, общий для всех пользователей в рамках текущей эпохи.

Внутри него:

- общая identity Хори;
- базовые правила ответа по контексту;
- ограничения на длину, анти-эссе, анти-ChatGPT;
- текущий epoch front, который задаёт радикальную шизовую окраску на несколько часов.

Важно:

- core не должен знать конкретного пользователя;
- core не должен включать relationship-состояние;
- core не должен содержать hooks;
- core должен быть одинаковым для всех чатов в рамках эпохи, чтобы хорошо ложиться в cache.

### Block 2. Callback Hooks

Это персональный короткий блок по текущему target-пользователю.

Здесь лежат до 5 persistent hooks.если в диалоге попадает ещё ктото то прям перед его сообщением появляется супер краткое пояснение что это хуки длч пользователя. и дается 2 последних хука.при глобальном сокращении на 46 сообщений доп хуки должны улететь в этот блок. при этом колическтво хуков начального пользователя тоже сокращается до 2 последних.
Каждый hook должен быть:

- коротким;
- понятным;
- не карикатурой из одной случайной фразы;
- с указанием, куда его можно применять;
- с запретом вспоминать его не к месту.

Задача блока не в том, чтобы приказать модели обязательно использовать hooks. Задача блока в том, чтобы дать ей разрешённые социальные рычаги, если текущий момент подходит.

### Block 3. Compacted Context

Этот блок стоит до текста живого чата.

Он содержит summary старых уже схлопнутых частей текущей сессии. Сюда не надо тащить всю сырую историю. Это плотная continuity-выжимка.

В compaction summary обязательно сохраняются:

- кто с кем спорил;
- кому Хори отвечала;
- какие линии всё ещё не закрыты;
- какие повторы и локальные мемы уже сформировались;
- где тема сменилась;
- какой пользователь сейчас был главной точкой напряжения перед хвостом.

### Block 4. Live Ladder Chat

Это главный живой блок.

В него попадают только:

- пользовательские сообщения;
- реально отправленные ответы Хори.

Порядок строго фактический: в том порядке, в котором реплики реально были отправлены.

Нельзя включать сюда:

- queued bot replies, которые ещё не ушли в Discord;
- внутренние черновики;
- неотправленные промежуточные куски;
- абстрактную общую ленту без адресации.

Если текущее сообщение прямо сейчас обрабатывается, оно временно добавляется самым последним элементом живого окна. Это единственный незавершённый ход, который допустимо видеть модели в момент ответа.

### Block 5. Relationship Tail

Relationship block стоит в самом конце.

Он должен быть маленьким, чётким и понятным. Не длинная психология, не prose, не essay.

Этот block всегда относится только к текущему target-пользователю.

Его назначение:

- зафиксировать дистанцию;
- зафиксировать допустимость троллинга;
- зафиксировать осторожность;
- дать дешёвой модели понятное правило обращения именно с этим человеком прямо сейчас.

## 4. Пример логической формы prompt

Ниже не буквальный production prompt, а схема того, как окно должно мыслиться.

```text
[CORE EPOCH]
единый глобальный core текущей эпохи

[CALLBACK HOOKS FOR TARGET]
- hook 1
- hook 2
- ...

[COMPACTED SESSION CONTEXT]
summary segment 1
summary segment 2
...

[LIVE CHAT WINDOW]
User: ...
Hori -> targetUser: ...
User: ...
Hori -> targetUser: ...
...
CurrentUser: ...

[RELATIONSHIP TAIL]
distance=...
mockery=...
caution=...
tone=...
```

Смысл такой:

- core задаёт мир;
- hooks задают личные социальные рычаги;
- compacted context даёт continuity;
- live ladder даёт актуальную сцену;
- relationship tail уточняет способ удара по текущему адресату.

## 5. Как именно должен работать live ladder block

### 5.1. Базовое правило

Block 4 собирается не из всей общей ленты канала, а из связанной сцены общения с Хори.

Туда входят:

1. пользовательские сообщения, которые попали в контур общения с Хори;
2. ответы Хори на эти сообщения;
3. всё это в реальном порядке, как оно было отправлено.

### 5.2. Что значит «связанный контур общения с Хори»

В контур попадает сообщение, если выполняется хотя бы одно из условий:

1. сообщение адресовано Хори напрямую;
2. сообщение реплаит на последнее сообщение Хори;
3. сообщение находится внутри активной reply-цепочки, где участвуют пользователь и Хори;
4. сообщение определено как текущий focus turn для Хори;
5. сообщение было тем сообщением, на которое Хори реально ответила позже.

### 5.3. Как включаются ответы Хори

Ответ Хори попадает в live ladder только после фактической отправки.

Нельзя заранее добавлять туда ещё не отправленный ответ, иначе модель начнёт видеть собственное будущее и путаться, а cache станет грязнее.

### 5.4. Что делать с сообщением в очереди

Если сообщение пользователя уже принято, но ответ Хори ещё висит в queue и не отправлен:

- пользовательское сообщение может быть в live ladder;
- предполагаемый bot reply в live ladder отсутствует;
- как только ответ реально отправлен, он добавляется в конец соответствующим ходом.

### 5.5. Что делать с текущим сообщением

Когда Хори прямо сейчас генерирует ответ на новое сообщение:

- текущее сообщение временно доклеивается в самый конец блока;
- это делается только transient-слоем для generation step;
- если ответ потом отправился, уже постоянный bot turn записывается отдельно как следующий элемент лестницы.

### 5.6. Явная маркировка ролей

Чтобы дешёвая модель не путалась, строки должны быть размечены предельно просто и единообразно.

Примерно так:

- `Пользователь -> Хори: ...`
- `Хори -> @username: ...`

Или аналогичный очень короткий формат.

Главное, чтобы у bot turns была явная адресация.

### 5.7. Обязательная metadata у bot turns

Для устойчивой мультиюзерной continuity у bot messages нужно хранить минимум:

- `targetUserId`
- `targetMessageId` по возможности

Без этого невозможно стабильно понять:

- кому именно Хори отвечала;
- к чьему relationship block относится хвост;
- на кого должны смотреть hooks;
- как восстанавливать лесенку после compaction.

## 6. Политика compaction

Это одна из главных правок пользователя. Ниже зафиксировано правильное правило.

### 6.1. Триггер

Compaction запускается не после 46 сообщений.

Правило должно быть таким:

1. Когда в unsummarized live ladder накопилось 54 элемента,
2. первые 46 элементов уходят в async compaction,
3. в live raw window остаётся хвост из 8 элементов,
4. после готовности summary старый сырой сегмент больше не подаётся как raw text.

### 6.2. Почему именно 54 / 46 / 8

Это даёт:

- длинный устойчивый блок для сжатия;
- очень маленький живой хвост;
- хороший cache behavior, потому что большая часть prompt стабилизируется summary-блоками;
- аккуратную лестничную структуру;
- лёгкую работу для дешёвой модели.

### 6.3. Что должен сохранять compactor

Compactor не должен писать литературное summary. Он должен сжать сцену технично и плотно.

Он обязан сохранить:

1. кто был главным спорщиком;
2. кто на кого наезжал;
3. кому Хори отвечала в ключевых местах;
4. какие темы уже фиксировались как локальный running bit;
5. что было решено, если было;
6. что осталось висеть незавершённым;
7. что нельзя потерять перед переходом к хвосту.

### 6.4. Что не должен делать compactor

1. Не писать красиво.
2. Не расписывать эмоции литературно.
3. Не повторять предыдущее summary.
4. Не тащить неважные случайные реплики.
5. Не превращать summary в рассказ от первого лица.
6. Не терять адресацию ответов Хори.

### 6.5. Как summary вставляется обратно

Когда summary готово:

1. оно попадает в Block 3: Compacted Context;
2. старые 46 raw-элементов больше не участвуют в live chat block;
3. свежий хвост остаётся в Block 4 без изменений;
4. следующие compaction cycles нарастают сверху новыми summary-сегментами.

### 6.6. Что анализируется после сессии

Когда Хори потом обновляет relationship и hooks, она не анализирует весь сырой лог заново. Она анализирует:

- все уже накопленные compacted segments текущей сессии;
- плюс оставшийся живой хвост.

То есть post-session analysis всегда работает по той же реальности, которую потом видел основной prompt.

## 7. Жизненный цикл сессии

### 7.1. Открытие

Сессия начинается с первого сообщения пользователя в новом контуре общения с Хори.

### 7.2. Активная стадия

Пока между релевантными сообщениями нет паузы больше 10 минут, сессия считается живой.

### 7.3. Закрытие

Если прошло 10 минут тишины:

- текущая сессия закрывается;
- live ladder больше не растёт;
- запускается post-session logic.

### 7.4. Sleep state

Если за сессию был хотя бы один compaction segment:

1. после закрытия сессии Хори уходит в sleep на 20 минут;
2. в это время она не отвечает никому;
3. по возможности её ник меняется на `спит`;
4. если смена ника не удалась, поведение sleep всё равно обязательно;
5. после sleep ник и normal reply behavior восстанавливаются.

### 7.5. Зачем нужен sleep

Sleep нужен не ради вайба сам по себе, а ради трёх функций:

1. дать окну сессии завершиться чёткой границей;
2. дать время на дешёвый offline analysis без нагрузки на hot path;
3. не заставлять Хори сразу влетать в новый тред с грязным старым контекстом.

## 8. Post-session analysis: relationship + hooks

Это второй главный столп системы после core epoch и live ladder.

### 8.1. Когда он запускается

Post-session analysis стартует после закрытия сессии.

Если был хотя бы один compaction, analysis выполняется в течение 20-минутного sleep window.

Если compaction не было, analysis всё равно можно запускать, но более лёгким режимом.

### 8.2. Кого анализировать

Анализируются только участники последней сессии.

Не все люди сервера. Не все люди канала. Только те, кто реально участвовал в последнем session window.

### 8.3. Порядок анализа

Участники идут по очереди, а не параллельно. Это дешевле и устойчивее.

Для каждого пользователя в evaluator подаётся:

- compacted session context;
- живой хвост;
- только нужные focus markers по этому человеку.

### 8.4. Relationship evaluator

Relationship evaluator должен быть тупым, коротким и enum-like.

Не prose-analysis. Не психологический essay.

Формат должен быть похож на набор простых вопросов с ограниченными вариантами.

Пример логики:

1. Какая дистанция сейчас точнее?
   - cold
   - neutral
   - familiar
   - close

2. Насколько допустим троллинг?
   - none
   - low
   - medium
   - high

3. Нужна ли осторожность?
   - no
   - mild
   - high

4. Какой основной тон вернее?
   - sharp
   - dry
   - neutral
   - warm

5. Есть ли короткая do/don't заметка?
   - optional small text

Итог relationship tail должен быть очень коротким и пригодным для prompt без раздувания.

### 8.5. Hook evaluator

Hook evaluator должен работать отдельно.

Его задача: найти persistent social hooks по человеку, а не абстрактные факты о нём.

Каждый hook должен отвечать на вопросы:

1. На что тут вообще можно цепляться?
2. За что на него уместно обижаться?
3. За что его можно троллить?
4. За что его можно стыдить?
5. Какая повторяющаяся нелепость или поза у него всплывает?

При этом evaluator обязан не раздувать мелочи.

### 8.6. Ограничения для hook evaluator

1. Максимум 5 hooks на пользователя.
2. Никаких hooks из случайной одноразовой реплики без продолжения.
3. Никаких hooks на темы, которые всплыли разово и умерли.
4. Никаких hooks, которые будут неуместны в 90% сцен.
5. Hook должен быть коротким, но с важной деталью.
6. Hook обязан иметь короткий tag или direction, где его применять.

### 8.7. Предлагаемая форма одного hook

Один hook логически должен иметь такие поля:

- `label` — короткое имя hook-а
- `detail` — короткая, но важная конкретизация
- `useTag` — куда это уместно применять
- `avoidTag` — где вспоминать нельзя
- `confidence` — насколько hook устойчивый
- `freshness` — насколько он ещё живой

### 8.8. Примеры useTag

Теги нужны не как taxonomy ради taxonomy, а как быстрый ключ уместности. Например:

- `tech_argument`
- `self_own`
- `stubborn_claim`
- `status_posturing`
- `excuse_spiral`
- `domestic_nonsense`
- `pet_topic`

### 8.9. Как hooks обновляются

Hooks не должны целиком переписываться на каждый session end.

Нужна merge-политика:

1. старые сильные hooks сохраняются;
2. новые устойчивые hooks могут заменить слабые;
3. протухшие hooks удаляются;
4. лимит 5 соблюдается всегда.

## 9. Relationship block: каким он должен быть

Relationship tail стоит в самом конце, но должен быть минимальным. Это сознательное решение пользователя.

### 9.1. Что в него входит

Минимальный состав:

- дистанция;
- допустимость mockery;
- осторожность;
- базовый тон;
- optional do/don't note в одну строку.

### 9.2. Что в него не входит

1. Длинный психологический разбор.
2. История отношений prose-текстом.
3. Полный список signal-ов.
4. Длинные explanation blocks.
5. Hooks. Hooks должны быть отдельным блоком выше.

### 9.3. Почему он стоит в конце

Потому что это последний корректирующий lens по текущему адресату, а не общая personality-инструкция. Он должен уточнять, как применять всё увиденное к конкретному человеку, уже после того как модель увидела core, hooks, summary и сам живой чат.

## 10. Core Epoch Manager

### 10.1. Основная идея

CorePrompt один на всех, но каждые несколько часов он может резко меняться. Это и есть контролируемая шиза в масштабах эпох.

### 10.2. Что остаётся неизменным

Во всех эпохах должны сохраняться:

- identity Хори;
- базовые ограничения по длине;
- правило отвечать по контексту;
- анти-эссе;
- анти-ботовость;
- общий стиль прямого короткого ответа.

### 10.3. Что меняется по эпохам

Меняется radical front:

- тип шизовой линзы;
- тип сухости;
- тип странной подачи;
- тип формализации или абсурда.

### 10.4. Почему epochs лучше, чем per-message randomness

1. Это лучше по cache.
2. Это даёт системе общую погоду на пару часов.
3. Это не делает Хори хаотично непоследовательной на каждом ходе.
4. Это даёт пользователям ощущение фаз, а не просто шума.

### 10.5. Требование к реализации

Epoch manager должен держать очень маленькое глобальное состояние:

- `epochId`
- `frontId`
- `startedAt`
- `expiresAt`

Именно это состояние определяет, какой core text сейчас общий для всех.

## 11. Горячий runtime pipeline

Ниже зафиксирован желаемый runtime flow одного incoming message.

### Step 1. Принять входящее сообщение

Понять, релевантно ли оно Хори и не находится ли бот в sleep state.

### Step 2. Проверить sleep

Если активен sleep:

- Хори не отвечает;
- сообщение может быть залогировано, но в hot generation path не идёт.

### Step 3. Определить target user

Даже если пишет один из нескольких участников, система должна выбрать, кому именно адресуется следующий ход Хори.

### Step 4. Собрать live ladder

Берутся только реальные отправленные user/Hori turns в фактическом порядке + текущее входящее сообщение как transient final element.

### Step 5. Проверить compaction threshold

Если несжатый live ladder достиг 54 элементов:

- первые 46 отправляются в async compaction;
- хвост остаётся жить дальше;
- generation текущего ответа не должен ждать конца compaction, если архитектура позволяет работать по уже существующим данным.

### Step 6. Собрать compacted context

Все готовые summary-сегменты текущей сессии подаются перед живым чатом.

### Step 7. Подтянуть hooks и relationship tail по target user

Только по одному человеку, а не по всем участникам сразу.

### Step 8. Собрать prompt

Порядок жёстко фиксирован: core epoch -> hooks -> compacted context -> live ladder -> relationship tail.

### Step 9. Сгенерировать ответ

Дешёвая модель видит стабильную форму и не плавает между чужими relationship-состояниями.

### Step 10. Отправить ответ

Только после фактической отправки записать новый bot turn с target metadata и включить его в историю.

## 14. Риски и меры предосторожности

### Риск 1. Модель путает, кому именно отвечает Хори

Решение:

- хранить target metadata у bot turns;
- явно маркировать адресацию в live ladder;
- держать relationship block только по одному target user.

### Риск 2. Hooks становятся тупой свалкой микромелочей

Решение:

- жёсткий лимит 5;
- обязательный useTag;
- запрет на hooks из одноразовых реплик;
- freshness/merge logic.

### Риск 3. Summary теряет социальную структуру сцены

Решение:

- обязать compactor сохранять адресацию и конфликтные линии;
- тестировать recovery контекста после compaction.

### Риск 4. Sleep ломает UX

Решение:

- sleep включать только если был хотя бы один compaction;
- nickname rename делать best effort;
- поведение silence важнее визуального rename.

### Риск 5. Core epochs слишком резко ломают образ Хори

Решение:

- фиксировать identity как неизменную часть core;
- менять только front layer;
- не делать epochs слишком часто.

## 16. Что считать готовой системой

Система считается реализованной только если одновременно выполняются все условия:

1. Один общий core действительно живёт эпохами и не меняется по пользователям.
2. Live chat block действительно состоит только из sent user/Hori turns.
3. Очередь не загрязняет prompt неотправленными bot replies.
4. При 54 элементах первые 46 реально уходят в compaction.
5. Summary действительно вставляется перед текстом живого чата.
6. Relationship block действительно стоит в самом конце и остаётся маленьким.
7. Hooks действительно persistent, короткие и не плодятся из мелочи.
8. После 10 минут silence сессия закрывается.
9. При наличии compaction Хори действительно уходит в 20-minute sleep и в это время не отвечает.
10. Во время sleep действительно обновляются relationship и hooks по участникам последней сессии.
11. В мультиюзерной сцене Хори не путает target user чаще допустимого минимума.
